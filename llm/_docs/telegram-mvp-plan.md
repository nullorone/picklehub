# Telegram MVP: требования и план коротких шагов

Дата интервью: 2026-09-24. Пилот: Москва. Бюджет: 3 дня × 8 часов.
Статус: требования согласованы; реализация шагов ниже ещё не начата.

Каждый шаг оформлен отдельным Markdown-файлом в [`llm/tasks/`](../tasks/README.md).
Для выполнения открыть соответствующий файл; таблицы ниже дают общий план распределения времени.

## Результат первого релиза

Пользователь открывает Mini App через существующего бота, создаёт игру и делится ссылкой.
Другой пользователь открывает игру, записывается и появляется в составе. Данные сохраняются на backend.
Организатор управляет составом, редактирует и отменяет встречу. Бот уведомляет об изменениях и напоминает.

Встреча — период игры с лимитом участников, например 8–16 человек. Организатор распределяет игроков
на площадке; алгоритмов ротации, назначения кортов и расписания раундов в первом релизе нет.

## Согласованные правила

- Любой авторизованный игрок может создать встречу. Запись автоматическая, без одобрения.
- Поля: название площадки, адрес, дата, время начала, длительность, лимит участников,
  желаемый уровень и необязательное описание. Площадка вводится вручную, без каталога и геокодинга.
- «Я участвую» включено по умолчанию. При выключении организатор управляет встречей, не занимая место.
- Один аккаунт занимает одно место. Организатор-участник учитывается в общем лимите.
- Игрок может выйти до начала. При заполнении запись закрывается, после освобождения места возобновляется.
- Организатор может удалить участника и отменить встречу. Очередь ожидания и запись друзей отложены.
- Бот открывает приложение и конкретную игру, сообщает об отмене и изменениях, напоминает за два часа.
  Напоминание получают текущие участники. Для личных уведомлений предусмотрен запуск бота пользователем.
- Визуальная основа — текущий интерфейс, включая светлую и тёмную темы. Полная дизайн-система — после MVP.
- Стили — Tailwind. Данные сервера — TanStack Query; Zustand добавляется только под конкретную задачу.
- Последовательность платформ: Telegram → web с необходимыми отличиями и PWA → React Native/магазины.

## Рабочие допущения для первого контракта

Следующие детали предложены при составлении плана, а не получены как отдельные ответы интервью.
Их можно изменить перед реализацией соответствующего шага.

- Игры доступны в общем списке будущих встреч и по ссылке; приватные встречи отложены.
- Желаемый уровень является подсказкой, не блокирует запись и не требует отдельного профиля или DUPR.
- Создание и изменение времени требуют будущей даты. Запись и выход закрываются после начала и при отмене.
- Уменьшение лимита ниже текущего числа участников отклоняется; автоматического исключения людей нет.
- Организатор может выключить собственное участие, сохраняя управление. Обратное включение занимает
  свободное место по тем же правилам, что обычная запись.
- Удалённый участник получает уведомление. Удаление освобождает место, но не является блокировкой аккаунта.
- Уведомления об изменениях отправляются при изменении площадки, адреса, времени, длительности,
  лимита, уровня или описания. Обычные записи и выходы не создают массовую рассылку.
- Организатор получает служебные уведомления и без участия; напоминание за два часа — только при участии.
- Если игрок записался менее чем за два часа до начала, отдельное просроченное напоминание не отправляется.
  При переносе времени старое задание аннулируется, новое создаётся, если его срок ещё впереди.
- При отправке повторно проверяются актуальные время, статус и состав; вышедшие не получают напоминание.
  Повторы обработки не должны создавать новые задания. Абсолютная однократность доставки через внешний
  Telegram API не гарантируется при неопределённом результате сетевого запроса; это учитывается в повторах.
- Время хранится в UTC, отображается в часовом поясе пользователя с явной подписью.
  В пилоте время московской площадки вводится в `Europe/Moscow`; преобразование видно в подтверждении формы.

## Технические границы

```text
backend/                 NestJS, Prisma, бот, обработчик уведомлений
frontend/tg/             React Mini App
frontend/packages/api/   сгенерированный API-клиент
frontend/packages/tokens/ минимальный источник общих дизайн-токенов
contracts/               TypeSpec → OpenAPI
llm/_docs/               решения, план, журнал
```

`frontend/web/` и `frontend/mobile/` создаются в следующих релизах. Общие доменные пакеты выделяются
по мере появления использования; UI между платформами переносится осознанно.

```text
MatchCard/
    MatchCard.tsx
    MatchCard.module.css
    helpers/
    hooks/
    api/
    __tests__/
    types.ts
    const.ts
    mock.ts
```

Элементы структуры создаются по необходимости. Основные стили — Tailwind; CSS Module нужен только
при наличии локальных CSS-правил. Названия вроде `MatchCard` приведены как пример, доменная сущность — встреча.
Токены задают смысловые цвета, отступы, размеры текста и скругления; значения доступны через тему Tailwind.
Для будущего React Native сохраняется источник значений, независимый от CSS и браузерных компонентов.

Текущий `start:https` запускает Vite с mkcert. `deploy` через `predeploy` собирает frontend и публикует
его в GitHub Pages. После переноса в workspace корневые команды сохраняют эти возможности.
Для backend потребуется отдельный HTTPS-адрес; GitHub Pages не выполняет NestJS и фоновые задания.
Токен бота хранится только на backend, данные Telegram проверяются сервером. Отладочный вход и моки
не должны разрешать доступ в среде пилота.

## План: 20 шагов по 60 минут и 4 часа резерва

Один шаг — одна рабочая сессия, включая относящиеся к нему проверки и запись в журнал.
Если шаг занимает больше часа, работа продолжается с него; следующий шаг не запускается до приёмки.
Оценки предварительные. Резерв не заменяет проверки, объём остатка пересчитывается по фактическому прогрессу.

Четыре резервных часа используются отдельными сессиями по 30–60 минут для незавершённых шагов,
исправлений и повторных проверок. Подключение хостинга может потребовать данных или действий владельца;
это не считается выполненным размещением. До выбора провайдера проверяются условия и размещение данных.
Публичная публикация выполняется только в рамках явно согласованного запуска.

## Проверки и завершение шага

- Для затронутого приложения: форматирование, линт, TypeScript, относящиеся тесты, контрактные проверки и сборка.
- При изменении контракта: генерация воспроизводима, клиент не редактируется вручную, HTTP-моки согласованы.
- Серверные сценарии: проверка Telegram, права организатора, повторная запись, конкурентное последнее место,
  выход и удаление, отмена, уменьшение лимита, устойчивость уведомлений и актуальность напоминаний.
- Интерфейс: загрузка, пустые данные, ошибка, отсутствие сети; успех записи показывается после ответа API.
- Реальный Telegram: два аккаунта, ссылки на игру, /start, сообщения об изменениях и напоминание.
- Для документов: форматирование Markdown, относительные ссылки и `git diff --check`.
- Точные команды, результаты и оставшиеся ограничения записываются в `ai-development-log.md`.

Конкретные npm-команды проверок создаются в `S01` для frontend и `S09` для backend.
Нельзя выдавать проверки моков за проверку настоящего backend или запуск на ноутбуке за постоянный пилот.
