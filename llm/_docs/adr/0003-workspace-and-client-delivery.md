# ADR 0003. Рабочее пространство и поставка клиентов

- Статус: принято
- Дата: 2026-09-03

## Контекст

PickleHub должен развивать backend, Telegram Mini App и web/PWA независимо, сохраняя единые wire-контракты.
Команда и бюджет MVP малы, React Native нужен только после стабилизации API, а перенос UI между разными
платформами создаёт связанность и ухудшает platform-specific UX.

## Решение

Использовать npm workspaces с единственным root `package-lock.json` и Turborepo для графа `build`, `lint`, `test`,
`typecheck` и разработки. Поддерживаемые workspace paths: `backend`, `frontend/web`, `frontend/tg`, отложенный
`frontend/mobile` и framework-neutral пакеты в `frontend/packages/*`.

Общие пакеты ограничены сгенерированным API client, domain helpers, validation, i18n и analytics taxonomy. Они не
содержат React-компоненты и не импортируют DOM, Telegram SDK, Expo/React Native, backend или код приложений.
Приложения зависят от общих пакетов, но не друг от друга; backend не зависит от frontend packages.

`frontend/web` поставляется как самостоятельное React/Vite-приложение и устанавливаемая PWA. Service worker
кэширует версионированную оболочку и безопасные данные только для чтения; мутации требуют сети и подтверждённого
ответа сервера. Административные маршруты живут в web, но используют отдельную авторизацию и не попадают в TMA.

`frontend/tg` поставляется отдельным React/Vite bundle, использует Telegram SDK только через свой platform adapter
и получает бизнес-данные через тот же сгенерированный API client. Различия навигации и UI не выносятся в общий UI
package.

`frontend/mobile` не создаётся до этапа `14-mobile-parity`. Его разработка начинается после стабилизации API и
измерения потребности; будущий клиент переиспользует wire-contract client и framework-neutral правила, но имеет
свой UI, навигацию, secure storage и lifecycle.

## Последствия

- Единственный lockfile и закреплённые версии инструментов делают локальную среду и CI воспроизводимыми.
- Turbo выполняет проверки только затронутого графа, не превращаясь в источник package versions или контрактов.
- Web/PWA и TMA могут выпускаться независимо и сохранять нативное для канала поведение.
- Изменение OpenAPI/AsyncAPI требует регенерации и проверки всех затронутых клиентов в том же изменении.
- Дублирование небольшого platform-specific UI допустимо; общий UI добавляется только новым ADR после доказанной
  одинаковой семантики и стоимости сопровождения.
- Отложенный mobile не создаёт преждевременный третий UI и не заставляет замораживать ещё не проверенный API.

## Отклонённые варианты

- Один React bundle для web и TMA: усложняет безопасность, маршрутизацию и независимую поставку каналов.
- Общая библиотека UI для web, TMA и mobile с первого дня: смешивает DOM и native primitives до появления
  подтверждённых общих компонентов.
- Создание Expo skeleton сейчас: нарушает порядок поставки и создаёт неиспользуемую поверхность обновлений.
- Несколько lockfiles или package managers: допускают расхождение инструментов и транзитивных зависимостей.
