# ADR-001: Telegram MVP и разработка frontend-first

Дата: 2026-09-24. Статус: принято по результатам интервью с владельцем проекта.

## Контекст

Прежний план требовал широкой платформы и одновременного запуска TMA/web. Владелец уточнил цель:
пилот в Москве за три дня по восемь часов, с работой по 30–60 минут. Основная потребность — создать
игровую встречу на время и собрать участников. Организатор самостоятельно распределяет пары и корты.

## Решение

- Активным маршрутом становится [план Telegram MVP](telegram-mvp-plan.md).
  Прежние каталоги `01`–`16` остаются отложенным контекстом; их полное прохождение не требуется до пилота.
- Сначала Telegram bot и Mini App; затем web/PWA, затем React Native для Android и iOS.
- Основа — npm workspaces, строгий TypeScript, React/Vite, Tailwind, TanStack Query,
  NestJS, Prisma и PostgreSQL. Географические координаты при их появлении хранятся в PostGIS.
- TypeSpec — редактируемый источник REST, OpenAPI и клиент генерируются. Моки работают на границе HTTP,
  поэтому подключение backend не требует другой модели данных в компонентах.
- AsyncAPI применяется при появлении событийных контрактов; отдельный WebSocket в первый MVP не входит.
- Дизайн текущего прототипа сохраняется как ориентир. Общие токены цветов, типографики, размеров и скруглений
  задаются сразу; полная библиотека общих UI-паттернов строится после MVP.
- Структура компонентов сохраняет локальные `helpers`, `hooks`, `api`, `__tests__`, `types.ts`,
  `const.ts`, `mock.ts`. Tailwind — основной способ оформления; `Компонент.module.css` создаётся
  для необходимых локальных CSS-правил. Пустые файлы и каталоги не обязательны.
- Минимальная основа создаётся до продуктового кода. Изменение требований предшествует контракту и реализации.
- Конкретный механизм устойчивой доставки уведомлений выбирается в `S10`; запись задания должна переживать
  перезапуск и быть согласованной с изменением встречи. Redis/BullMQ не является обязательным условием
  начала frontend-разработки.

## Последствия

Модель встречи не ограничивается двумя или четырьмя игроками. Организатор и участник — независимые роли
внутри встречи. Очередь, заявки, гости, счёт, чат, карта и турниры не входят в пилот.

GitHub Pages обслуживает frontend. Для пилота нужны HTTPS API, PostgreSQL и работающий обработчик
уведомлений. Локальный HTTPS через mkcert не предоставляет публичный туннель. Хостинг пока не выбран;
его выбор и проверка условий входят в план, размещение персональных данных должно учитывать правила проекта.

24 часа — бюджет попытки запуска. Невыполненные проверки или отсутствие работающего backend
не позволяют считать пилот завершённым; перерасход отражается в журнале и оценке срока.
