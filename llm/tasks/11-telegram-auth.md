# S11. Telegram-вход и сессия

Статус: выполнена. День 2. Бюджет одной сессии: 30–60 минут, плановая оценка — 60 минут.
Предыдущая задача: [10-prisma-jobs.md](10-prisma-jobs.md).

## Цель

Получать достоверную пользовательскую идентичность на backend.

## Перед началом

Прочитай корневой `AGENTS.md`, [обзор проекта](../00-project-overview.md),
[порядок работы](../README.md), [требования MVP](../_docs/telegram-mvp-plan.md),
[ADR-001](../_docs/adr-001-telegram-first-mvp.md) и
[результаты предыдущих задач](../_docs/ai-development-log.md).
Если приёмка предыдущего шага не завершена, сначала закончи его.

- Контракт сессии S03, конфигурация S09, Prisma S10.
- Актуальные официальные правила проверки Telegram Mini App initData.

## Выполнить

1. Реализовать серверную проверку подписи и срока initData по официальным правилам Telegram.
2. Создавать/находить пользователя по проверенной идентичности; не доверять userId из произвольного тела запроса.
3. Реализовать сессию, истечение и восстановление входа; задокументировать хранение credential для раздельных frontend/API-origin.
4. Добавить защиту маршрутов, ограничение частоты входа и ошибки по контракту.
5. Убедиться, что dev-моки не разрешены в пилоте, а initData, токен бота и сессионные данные не попадают в логи.

## Критерии готовности

- [x] Корректный вход создаёт рабочую сессию; неверная подпись и просроченные данные отклоняются.
- [x] Frontend получает собственную идентичность через API; изменение клиентского userId не подменяет пользователя.
- [x] Проверки выполнены, точные команды и результаты записаны в журнал.

## Проверки

- Форматирование, линт, типы, тесты валидного/поддельного/просроченного входа, контрактные проверки и сборка.
- Проверить редактирование логов и истечение сессии на синтетических данных.
- Выполнить `git diff --check`; проверить ссылки и форматирование изменённых документов.
- Не ослаблять проверки и не выдавать непроведённые проверки за успешные.

Не добавлять email/magic link, связывание аккаунтов, DUPR и расширенный профиль.
