# PickleHub: единый контекст реализации

Этот файл — источник стабильного продуктового контекста. Агент читает его перед каждым этапом и не расширяет scope без ADR и изменения связанных требований.

## 1. Цель и рынок

PickleHub помогает русскоязычным игрокам в pickleball перейти от намерения поиграть к подтверждённому состоявшемуся матчу. Первый рынок — Россия/СНГ, основной канал привлечения — локальные Telegram-сообщества. Это реальный low-budget startup MVP, а не демонстрационный макет.

North-star — число подтверждённых состоявшихся матчей в неделю. Активация — завершённый onboarding. Пилот подтверждает гипотезу, если не менее 50% опубликованных матчей, получивших хотя бы одну заявку, завершаются подтверждённой игрой; решение принимается на выборке не менее 30 подходящих матчей.

## 2. Релизы

### Match MVP

- единый аккаунт через Telegram или email magic link;
- onboarding, самооценка уровня и публичный профиль;
- OSM и пользовательский каталог публичных площадок;
- карта, список, фильтры и объяснимые рекомендации матчей;
- создание 1×1 и 2×2, auto-join или заявки, очередь и места гостей;
- публичные матчи и матчи по ссылке;
- текстовый чат, системные события и in-app/Telegram/email уведомления;
- счёт по партиям, подтверждение результата соперником, история и статистика;
- отзывы, no-show, жалобы, блокировки и минимальный backoffice;
- TMA и web/PWA с функциональным паритетом.

### Последующие релизы

1. Клубы и регулярные клубные встречи.
2. Tournament engine со всеми восемью форматами.
3. Глобальная и клубная геймификация.
4. Редакционная CMS новостей и рекламный inventory.
5. React Native/Expo.
6. Общая web-мини-игра для браузерных клиентов и mobile WebView.
7. Декларативный DSL пользовательских турнирных форматов.

## 3. Пользователи и роли

- `Player`: ищет, создаёт и играет матчи, состоит в клубах и турнирах.
- `Match organizer`: владелец конкретной встречи; это не platform-role.
- `Club owner/admin/member`: scoped-роли внутри клуба.
- `Tournament organizer`: управляет конкретным турниром и результатами.
- `Superadmin`, `Moderator`, `Editor`, `Ads manager`: раздельные platform-роли с аудитом.
- `Guest placeholder`: место реального игрока без аккаунта; не получает профиль и статистику.

## 4. Матчевые правила

- Форматы: singles `1×1` и doubles `2×2`.
- Видимость: `PUBLIC` или `UNLISTED`; unlisted открывается по непредсказуемой ссылке и не попадает в поиск.
- Вступление: `AUTO` либо `APPROVAL`. Ограничения состава — формат и диапазон самооценки уровня, без пола и возраста.
- Полный матч поддерживает FIFO waitlist. В auto-режиме освободившееся место получает первый подходящий кандидат; в approval-режиме организатор подтверждает предложенного кандидата.
- Обычные матчи разовые. Повторение расписания появляется только у клубов.
- Корт не бронируется и не оплачивается внутри MVP; хранится только указанная организатором информация о внешней брони.
- Организатор вносит победителя и счёт партий либо только подтверждает факт игры без результата. Хотя бы один зарегистрированный игрок противоположной стороны должен подтвердить.
- Спорный результат не меняет статистику до решения moderator. Повторная обработка подтверждения не создаёт повторных начислений.

## 5. Площадки

- Seed берётся из OpenStreetMap/Overpass только с соблюдением ODbL, attribution и правил выбранного tile provider.
- Поиск адреса и геокодинг реализуются через provider adapter. Запрещено сохранять выдачу Yandex/2GIS или другого сервиса, если условия этого не разрешают.
- Игрок может задать новую публичную спортивную площадку. После состоявшегося матча она становится кандидатом общего каталога, проходит нормализацию, proximity-дедупликацию и модерацию.
- Частные домашние адреса запрещены. Точные адреса разрешённых площадок видны всем пользователям.

## 6. Identity, профиль и DUPR

- Один пользователь связывает Telegram identity и email magic-link identity.
- Backend проверяет Telegram init data; magic links одноразовые, короткоживущие и хранятся только как hash.
- Стартовый уровень — неподтверждённая самооценка. Внутренние результаты дают статистику, но автоматически не меняют DUPR.
- DUPR MVP хранит внешний ID/ссылку. API adapter остаётся выключенным до официального доступа; scraping и выдача ручного значения за подтверждённое запрещены.
- Возраст не проверяется. Это принятый legal/safety risk, который не следует скрывать.

## 7. Клубы и турниры

- Клуб — сообщество с нулём или несколькими площадками. Вступление открытое, по заявке либо invite-only.
- Турнир принимает игроков и готовые пары. Платное событие хранит цену/валюту и ручной внешний payment status; платёж через PickleHub отсутствует.
- Форматы: `AMERICANO`, `ROUND_ROBIN`, `SINGLE_ELIMINATION`, `DOUBLE_ELIMINATION`, `POOL_PLAY`, `SWISS`, `LADDER`, `KING_OF_COURT`.
- Каждый формат — versioned strategy над общей моделью entrants/stages/rounds/matches/standings. Организатор выбирает preset и безопасные параметры.
- Поздний custom format — валидируемый декларативный DSL. Нельзя выполнять пользовательский JavaScript через `eval`, VM текущего API или другой непроверенный runtime.

## 8. Контент, реклама и геймификация

- Редакторы публикуют оригинальные статьи или переработанные материалы из разрешённых RSS/API. Всегда сохраняются источник, авторство и ссылка; автопубликации нет.
- Пользователь читает, сохраняет и делится статьёй; публичных комментариев в первой версии нет.
- Прямая реклама и внешний network fallback используют общий inventory. Таргетинг только контекстный и географический, без чувствительных профилей и точных перемещений.
- Placement существует на любом экране, но не перекрывает ввод счёта, подтверждение, жалобу, системную ошибку или другое критическое действие. Нужны маркировка и frequency caps.
- Глобальный XP награждает подтверждённое участие и полезный вклад, а не победы. Клубы настраивают коэффициенты только через безопасные шаблоны. Лидерборды сезонные и opt-in.

## 9. Технологический baseline

- npm workspaces + Turborepo, Node.js 22, strict TypeScript.
- Backend: NestJS modular monolith, Prisma, PostgreSQL/PostGIS, Redis/BullMQ, transactional outbox.
- Contracts: OpenAPI для REST, AsyncAPI для WebSocket и событий; generated clients не редактируются вручную.
- Frontend: React/Vite web/PWA, отдельный React TMA, React Native/Expo позже.
- Shared: API SDK, domain types, validation, i18n и analytics taxonomy; UI остаётся platform-specific.
- Object storage: S3-compatible provider для медиа.
- Deployment: low-budget managed infrastructure с локализацией персональных данных в РФ и обязательной юридической проверкой.

## 10. Нефункциональные требования

- Database constraints, idempotency и транзакции защищают последнее место, подтверждение результата, XP ledger и outbox от гонок.
- Время хранится в UTC, отображается в timezone пользователя. География хранится и ищется через PostGIS.
- Structured logs, request/correlation ID, audit log, metrics, tracing/error reporting и redaction обязательны.
- Нельзя логировать init data, токены, magic links, email, chat text, точные перемещения или advertising identifiers.
- Интерфейс русский и i18n-ready, доступен с клавиатуры, адаптивен и имеет loading/empty/error/offline/success состояния.
- PWA кеширует shell и read-only данные; мутации требуют сети и не должны создавать ложный optimistic success.
- Production изменения выполняются миграциями; нужны backup/restore, graceful shutdown, readiness/liveness и rate limits.

## 11. Явные non-goals текущего scope

- встроенные бронирование и оплата кортов;
- Premium entitlements и любые реальные платежи;
- проверка возраста или документов;
- ML-рекомендации;
- изображения/файлы/голос в чате;
- автоматическое изменение DUPR;
- автопубликация внешних статей;
- пользовательский JavaScript для турнирных правил;
- микросервисы, Kubernetes и отдельный search cluster.
